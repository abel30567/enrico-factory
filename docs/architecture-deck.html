enrico-factory: the content factory

A story ships like a ticket: one maker per artifact, a checker that did not write it, and a merge that locks it

Before
One session researches, writes, boards and generates. It judges its own work, and the state lives in chat.
With the factory
A showrunner files tickets as issues. A maker delivers one artifact per pull request. A checker gives notes on the exact commit. A merge is the lock, and GitHub is the only state.

Six differences from the software kit, and why this is a new system

  • Roles are data: one file per studio role. A stage ladder with locks: cheap stages first
  • Rooms: several makers pitch one ticket. Notes with severity: only a Blocker stops a lock
  • Canon is protected and marks broken work stale. Provenance is tagged on every fact

Lead with the parallel: this is the orchestrator, builder and verifier pattern, moved from code to story. The showrunner is the orchestrator, a maker is a builder, a checker is a verifier, and a merge is a lock.

Be plain about status: as of 2026-11-11 the architecture and the brief are written and the repository is public. Wave 1 of the build has not started, so nothing in this deck is a measured result.

If asked why a new system and not the same kit: the six differences on the left. Each one exists because story work has stages, canon and taste, which code does not.

enrico-factory · Content factory architecture
Where the system lives

enrico-factory is built with the software kit, and what it builds is a second kit that runs one production per repository

Lead with the split. Layer 1 is ordinary software work: builders and verifiers write the kit through pull requests, and the orchestrator merges. Layer 2 is a production: a series in its own repository, run by a showrunner with studio roles.

The only connection between the two is factory init, which installs the kit into a production repository as .factory/.

Every later slide describes layer 2.

enrico-factory · Content factory architecture
Interaction map: every connection and what travels on it

The showrunner is the only node that merges or spends; workers reach GitHub and their own worktree, and GitHub holds all the state

Lead with the hub. Tickets, launches, rulings, greenlights, paid jobs and the lock all go through the showrunner's session. Workers have two connections: they are launched with a rendered prompt and a worktree, and they talk to GitHub through a branch, a pull request and first-line markers.

Three facts hold the system together. GitHub is the only state. Makers and checkers never share a worktree and never merge. Anything that spends money or cannot be undone runs in the showrunner's session.

The paid jobs and the media store are planned, not in v0.

enrico-factory · Content factory architecture
Data flow: the stage ladder

Work climbs a ladder of locked stages, cheapest first, so a bad idea fails on paper before anything is rendered

G owner greenlight · solid boxes are v0 · dashed grey boxes are planned · dashed bypass: short formats skip outline · dotted lines: bytes go to the media store, only a manifest row is committed

Lead with the rule: a stage must be locked before the next stage of the same unit may start. A unit is a research topic, a canon change or an episode.

Only files on main travel between stages. A maker starts from a worktree of the current base, so it sees canon and every locked upstream artifact and nothing unfinished.

Every factual line carries a provenance tag: text, art, inferred or invented. An invention made at the premise stage is still visibly an invention at the board stage.

If asked about media: files are never committed. A job writes the bytes to the store and commits one manifest row with the hash, which changes the head, so a verdict on a commit is a verdict on exact bytes.

enrico-factory · Content factory architecture
Process map: one beats ticket across five lanes

One ticket crosses five lanes from issue to lock, and the owner appears in a single column: the greenlight

Lead with the dashed band in the owner lane. While the artifact is made, checked and fixed, the owner is not involved. A choice that can be undone is settled by a showrunner ruling posted on the ticket.

Follow the numbers: 1 file the ticket, 2 launch the maker, 3 the maker writes and posts READY, 4 the checker posts NOTES on that head, 5 the maker is relaunched and posts ADDRESSED, 6 a fresh checker posts APPROVED on the new head, 7 the owner's greenlight where the stage needs one, 8 the lock.

Nothing starts a worker automatically. A worker posts a marker and exits, factory status reads the markers, and the showrunner launches the next role.

This example uses a beats ticket, which needs no greenlight. Column 7 applies to the premise and board stages.

A ticket's life on GitHub

A ticket's state is never set by hand: it is derived from labels and the newest first-line marker

Maker markers, on the pull request[<ROLE>] READY head SHA, lint table, evidence per criterion · ADDRESSED the change and commit per note · BLOCKED missing, tried, resume from
Checker markers, on the pull request[<ROLE>] NOTES N1..Nn, each a Blocker or an Issue · APPROVED evidence per criterion. Both carry Reviewed head <sha>
Showrunner markers, on the issue[SHOWRUNNER] LAUNCH the exact prompt, sha256, model, base · RULING · SELECTED #<pr> · GREENLIGHT the owner's words and date

Lead with "derived". Nobody drags a card. A new session rebuilds the whole picture from issues, pull requests, labels and markers.

Only the first line of a comment counts as a marker. A checker verdict counts only if it is newer than the maker's last READY or ADDRESSED, names the current head, and comes from the checker the pipeline names for that stage.

After three rounds of notes on one pull request the showrunner rules.

enrico-factory · Content factory architecture
The writers' room: one ticket, several pitches

A room turns one premise ticket into three competing pull requests, and exactly one of them is locked

Lead with the studio practice: several writers pitch, one idea is chosen. This is the one place where a ticket has more than one pull request.

One checker reads all three pitches and scores them on one rubric, so the scores are comparable. The showrunner selects and posts the reason. The owner greenlights. The lock merges the selected pitch and the others are closed.

In v0 only the premise stage runs as a room.

enrico-factory · Content factory architecture
The one change that can break locked work

Canon changes only through its own pull request, and a locked change marks the work it breaks as stale

Lead with why canon is special: every story stage builds on it, so it is the only change that can invalidate work already locked.

The canon-reviewer plays the part the blast-radius reviewer plays in the software kit: it lists the locked artifacts that relied on the old text. After the lock, the showrunner files one revision ticket per broken unit at the earliest broken stage, and later stages of that unit wait.

A writer cannot change canon inside a script: any pull request that touches canon/** needs APPROVED from the canon-reviewer, whatever its stage.

Open question, be honest: how a locked artifact pins the canon it relied on (cited path or content hash) is not decided. Until then the stale list comes from the canon-reviewer.

Trust boundaries, open questions, build order

Five boundaries are enforced at the lock, five design questions are open, and wave 1 of the build has not started

Enforced

  • Workers cannot merge. Only factory lock --apply merges, and it rechecks every rule from GitHub at that moment
  • Workers cannot spend. Generation, rendering and voice run only in the showrunner's session
  • A maker writes only inside its role's writes globs. The lock refuses anything else
  • A verdict is bound to a commit. A new commit, including a manifest row for new media, makes it stale
  • Launch prompts are public record: prompt, hash, model and base commit, posted before the worker starts
  • Known limit: workers run under the showrunner's GitHub login, so markers stop honest mistakes and drift, not deliberate forgery

Not decided yet

  • How a locked artifact pins the canon it relied on: by cited path, or by content hash
  • Whether factory lock holds a stale unit's later stages itself, or the showrunner does it with hold
  • The 3D toolchain. Blender is the pilot; nothing is chosen
  • The perceptual metric and its threshold, calibrated on approved references before it gates anything
  • Which stages run on a heartbeat without the showrunner, and when
Wave 1In parallel on disjoint files: role registry and launcher; nine role files and seven format files; pipeline, status and lock; lints

Lead with the known limit, because it is the honest part: the markers are an audit aid. Signed job records, which are planned, cover the media steps where forgery would matter most.

The open questions are design decisions, and none of them blocks wave 1.
